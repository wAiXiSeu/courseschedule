### 4.2 新增待确认问题

#### Q-new-1 ⭐ 双端数据同步方案（关键决策，阻塞架构设计）

> 客户说「小程序查看 + Web 管理后台」且「不需要云同步」，但两端如何共享同一份数据仍需明确。以下 3 种方案供客户选择：

| 方案 | 方案名称 | 工作方式 | 优点 | 缺点 | 复杂度 |
| --- | --- | --- | --- | --- | --- |
| **A** | **Web 为主 + 小程序只读镜像** | Web 端为唯一数据源（本地 IndexedDB），小程序端通过 Web 端生成的**分享链接/二维码**查看快照数据；打卡数据通过小程序本地存储 + 手动导出 | 无需后端，最简单；符合「不需要云同步」 | 小程序打卡数据无法实时反映到 Web 端；体验割裂 | ★☆☆ |
| **B** | **轻量后端 + 手动同步** | 部署一个轻量后端（如 Cloudflare Workers + D1/KV），两端各自操作后**手动触发同步**（点"同步"按钮）或打开时自动拉取最新 | 数据可跨端一致；后端极轻、无实时要求 | 需部署后端（有成本）；手动同步有延迟感 | ★★☆ |
| **C** | **Web 为主数据源 + 小程序仅展示** | Web 端完整读写（本地 IndexedDB），小程序端**纯展示**——通过 Web 端导出的静态 JSON/分享链接加载，**打卡也在 Web 端完成**；小程序仅作为「孩子随时查看」的便捷入口 | 完全无后端；数据一致性由 Web 端单一来源保证 | 孩子打卡必须用 Web 端，不符合「孩子用小程序打卡」的直觉 | ★☆☆ |

**推荐**：方案 B（轻量后端 + 手动/自动同步），虽然引入了后端，但复杂度很低（无实时要求、无账号体系），且能实现两端数据一致，是用户体验与技术成本的最佳平衡点。

#### Q-new-2 小程序端的身份识别方式

| 子方案 | 说明 |

## 8. 第三轮增量（2026-09-17）：补打卡

### 8.1 背景

此前全站没有任何入口能改「当前日期」，打卡页永远只处理今天，因此漏打就是永久丢失。`CheckInRecord.isMakeup` 字段自积分系统上线时已预埋（并预留了补卡打折的常量，后按 D13′ 取消），本轮把交互与统计口径补齐。

### 8.2 决策

| # | 决策 | 说明 |
| --- | --- | --- |
| D11 | 补卡形态：**按天补** | 计划卡片新增「补打卡」入口 → 选一天 → 列出该计划当天应完成的任务 → 勾选提交。一次把漏掉的一天补齐，不做逐条补 |
| D12 | 范围：**限过去 7 天（不含今天）**，**双端均可补** | 今天走打卡页；忘了打卡的往往就是孩子自己，故不设家长门禁 |
| D13′ | 分值：**与正常打卡同分**（推翻原 D13 的减半） | 孩子确实做了那件事，晚勾不该打折；补卡与正常打卡的唯一差别改为「不计入连续与里程碑」。⚠️ 积分是派生计算而非落库，改规则会**追溯重算**历史补卡记录的分值，余额会随之跳变 |
| D14 | 统计：**不计入连续天数与里程碑，但计入累计天数与本周格子** | 新增 `collectGenuineDates()`：某天至少有一条非补卡记录才算「真实打卡日」，连续与里程碑只看真实打卡日 |
| D15 | 满额奖：**照发** | 当天到期任务全部完成（含补齐）即给 +20，补卡不因此被区别对待 |
| D16 | 候选日：只提供**该任务当天已存在**的日子 | 复用积分满额奖同一条 `taskExistedOn()` 判定，避免出现「补了一天却没拿到满额奖」的口径错位。副作用：**今天新建的任务不能补昨天** |

| shared | `pointsForCheckin()` 简化为只按来源取分（删掉 `isMakeup` 参数与 `POINT_RULES.makeupMultiplier`）；`deriveDailyGoalEntries` 无需改动，满额奖天生照发 |
